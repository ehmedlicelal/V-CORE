## T1 — PSM 3 for two-column quiz sheets

**What:** Switch Tesseract from `--psm 6` (uniform text block) to `--psm 3` (automatic page segmentation) for two-column exam layouts.

**Why:** PSM 6 reads columns top-to-bottom as a single flow, producing garbled output on two-column sheets. PSM 3 auto-detects layout.

**Pros:** Correct OCR output for multi-column formats common in standardized tests.

**Cons:** PSM 3 is slower and occasionally over-segments single-column pages.

**Context:** File to change is `ocr-service/main.py:277` (`config="--psm 6"`). Also consider making PSM configurable via env var (`OCR_PSM=6`) in the Dockerfile so it can be tuned without a redeploy. Benchmark both modes on real scanned quiz sheets before switching.

**Depends on:** OCR service deployed and tested with real worksheets.

## T2 — Integration PR: wire parsePdfPages() into quiz creation flow

**What:** Build the question-grouping layer: `ParsedPage[]` (TextFragment[]) → `NewQuestion[]`, and add a new "PDF Parser" mode to the quiz creation UI.

**Why:** `parsePdfPages()` currently has no caller. The OCR layer is complete but the feature is not usable until questions can be extracted from the fragments.

**Pros:** Makes the OCR investment user-visible; teachers can upload scanned worksheets via the new mode.

**Cons:** Adds UI complexity; question-grouping accuracy needs validation on real sheets.

**Context:** Two approaches:
- (a) Pass raw extracted text to the existing Groq LLM extractor (same prompt as `parseQuizPdf.ts`) — fastest path, reuses existing infrastructure.
- (b) Rule-based grouping by y-coordinate and line spacing — deterministic but brittle.
Start with (a). The `wasOcrd: true` flag on `ParsedPage` lets the UI surface an accuracy warning when OCR was used.

**Depends on:** This PR (OCR layer) merged and deployed.

## T3 — Render deployment + CI/CD for OCR service

**What:** Create `.github/workflows/ocr-service-deploy.yml` that builds the Docker image on push to main and deploys to Render.

**Why:** Manual deploys create drift between the deployed service and the repo. A GitHub Actions workflow makes OCR service updates automatic.

**Pros:** Eliminates manual deploy step; OCR service stays in sync with code.

**Cons:** Requires Render API token in GitHub secrets; adds CI configuration to maintain.

**Context:** Render supports Docker deployments via `Dockerfile` in a subdirectory (`ocr-service/`). Important: Render's free web service tier ALSO spins down after inactivity (same as Railway free). Use Render Starter ($7/mo) OR add a health-ping cron (e.g., `cron-job.org` hitting `GET /health` every 10 minutes) to keep it alive. Set `OCR_SERVICE_URL=https://<your-service>.onrender.com` in Vercel project env vars after first deploy.

**Depends on:** OCR service first deployed manually to Render (get the service URL).
