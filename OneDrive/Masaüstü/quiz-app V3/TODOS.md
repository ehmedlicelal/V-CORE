## OCR Service (V3 Phase 2 — port from V2)

Security issues found in adversarial review before shipping. Fix before deploying OCR in production:

- [ ] **OCR: return HTTP 4xx/5xx on errors, not HTTP 200** (F2 — High)
  - **What:** The bare `except Exception` block returns `{"fragments": []}` with HTTP 200 on all failures. Next.js cannot distinguish "OCR returned nothing" from "Tesseract crashed."
  - **Fix:** Return HTTP 422 for invalid input, HTTP 500 for unexpected errors. Let `DecompressionBomb` propagate as 413.

- [ ] **OCR: add authentication header** (F4 — High)
  - **What:** No auth on `/ocr` endpoint. Acceptable for Docker dev (localhost-only) but must be secured before Railway/Fly.io deployment.
  - **Fix:** Require `X-OCR-Token` header checked against an env var secret, OR restrict the container to an internal Docker network with no public port mapping.

- [ ] **OCR: enforce file size limit and content-type check** (F1, F9 — High)
  - **What:** No size cap before `Image.open()` — a 500MB TIFF can OOM the container. No content-type check — non-image files accepted by Pillow.
  - **Fix:** Reject if `len(img_bytes) > MAX_BYTES` (e.g., 20MB). Check `content_type in {"image/png", "image/jpeg", "image/tiff", "image/webp"}` before reading.

- [ ] **OCR: add Tesseract request timeout** (F8 — Medium)
  - **What:** `pytesseract.image_to_data()` can block for minutes on complex high-res pages, freezing the single-worker uvicorn process.
  - **Fix:** Add `timeout=30` parameter; catch `TesseractError` and return HTTP 504.

- [ ] **OCR: add multilingual support** (F7 — Medium)
  - **What:** Dockerfile installs only `tesseract-ocr-eng`. Azerbaijani/Turkish exam sheets return garbled results silently.
  - **Fix:** Install `tesseract-ocr-tur` and/or `tesseract-ocr-aze` in Dockerfile; support `OCR_LANG` env var.

- [ ] **OCR: remove hardcoded style flags from response schema** (F5 — Low)
  - **What:** Every fragment returns `"bold": False, "italic": False` regardless of actual content. Misleading to downstream consumers.
  - **Fix:** Remove style fields or mark them explicitly as `"available": false` stubs.

## Phase 2

- [ ] **Supabase Realtime upgrade (dashboard)**
  - **What:** Upgrade tutor dashboard from 30s polling to Supabase Realtime subscription.
  - **Why:** 30s polling is acceptable for Phase 1 but creates perceptible lag on quiz day when students submit back-to-back. Likely to generate tutor complaints after real usage.
  - **Effort:** ~20 lines of code change. Supabase free tier includes Realtime.
  - **Depends on:** Phase 1 shipped + real tutor feedback confirming the lag is noticeable.

- [ ] **PDF import (Phase 2)**
  - **What:** Accept PDF upload in quiz creation flow. Extract questions using pdfjs (digital PDFs) and OCR microservice (scanned PDFs).
  - **Why:** Tutors currently retype all questions manually. PDF import removes this friction.
  - **Effort:** M (1-2 weeks). OCR microservice design already approved (`ehmed-main-design-ocr-microservice-20260621-183935.md`).
  - **Depends on:** Phase 1 validated with at least 3 non-builder tutors.

- [ ] **Phone-number student identity**
  - **What:** Replace name-only student identification with phone number entry.
  - **Why:** Name-only allows duplicate names and makes student progress tracking across quizzes impossible.
  - **Depends on:** Student progress history (Phase 3).

## Phase 3

- [ ] **Questions table migration**
  - **What:** Migrate `questions` JSONB column in Quiz table to a separate `questions` table.
  - **Why:** JSONB prevents cross-quiz question analytics (e.g., "which question do students fail most across all your quizzes?"). Phase 3 student progress history will need this.
  - **Effort:** S. Not a breaking change — additive migration + JOIN update everywhere.
  - **Depends on:** Student progress history feature.

- [ ] **Student progress history**
  - **What:** Per-student view showing quiz history, running score average, improving/declining trend.
  - **Why:** Tutors need to know which concepts a student consistently struggles with. Core long-term defensibility.
  - **See:** CEO plan `2026-06-03-tutor-quiz-app.md`.

- [ ] **WhatsApp score summary copy button**
  - **What:** One-click copy of formatted score summary for WhatsApp paste ("Quiz: Grammar Test — Ali: 8/10, Sara: 7/10, ...").
  - **Why:** Closes the WhatsApp loop. Tutors share results in the group even after switching to the link-based flow.
  - **Effort:** S (~30 min).

- [ ] **Viral footer on student submission page**
  - **What:** "Made with QuizLink" footer on the student quiz page. Toggle in tutor settings (default: on).
  - **Why:** Every quiz link = distribution event. Zero marginal cost.
  - **Effort:** S (~30 min).

- [ ] **Monetization / Stripe integration**
  - **What:** Free tier (5 quizzes/month) + Pro ($9/month, unlimited + history + export).
  - **Why:** Deferred until real usage patterns are visible.
  - **Depends on:** Real paying tutor intent, usage data from Phase 1-2.
